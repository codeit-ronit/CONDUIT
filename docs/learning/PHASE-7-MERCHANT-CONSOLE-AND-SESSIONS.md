# Phase 7, slice 3: Merchant console and durable sessions

## What did we build?

We turned the catalog provenance already stored in Phase 5 into a merchant-facing
product surface. A merchant signs in, receives a revocable database-backed browser
session, and sees only their own products. Each product displays current price and stock
alongside the source file, source column, recorded value, source type, and digest that
explain where its imported fields came from.

## The most important rule

The browser never tells the server which merchant to load.

```text
email + password
      ↓ scrypt comparison
random raw token → HttpOnly browser cookie
      ↓ SHA-256 digest lookup
active session → user membership → tenant + merchant
      ↓
scoped products + prices + stock + provenance
```

This prevents a common multi-tenant mistake: changing a merchant ID in an API request to
read somebody else's data. `/api/merchant/catalog` has no tenant or merchant input.

## What is stored?

- `merchant_users`: normalized email, display name, random password salt, scrypt digest.
- `merchant_memberships`: the user's server-controlled tenant, merchant, and role.
- `browser_sessions`: SHA-256 token digest, expiry, revocation, and last-seen time.

The raw password is never stored. The raw session token exists in the browser's
`HttpOnly` cookie, so normal page JavaScript cannot read it. PostgreSQL stores only the
token digest. Logout sets `revoked_at`; expired or revoked rows cannot authenticate.

## Why SHA-256 for sessions but scrypt for passwords?

Passwords are human-chosen and guessable, so they need deliberately expensive hashing
with a unique salt. Session tokens are 256 random bits generated by the server; they are
not guessable in the same way, so a one-way SHA-256 digest safely supports fast lookup.

## Why show provenance?

A price without a source is difficult to review. The console connects each imported
field to:

- the source file or storefront;
- the source path/column;
- the exact value observed during import;
- the source-content digest;
- the time evidence was recorded.

This makes merchant corrections and later audit explanations possible without trusting
the original file to remain available forever.

## Evidence

- Pure tests prove passwords/tokens are represented by digests, session scope reaches
  the repository, and logout invalidates the token.
- PostgreSQL tests create two merchants and prove the first merchant's session cannot
  see the second merchant's product.
- Reprovisioning an unchanged demo password preserves a valid session; changing the
  password revokes old sessions.
- A live HTTP run proves 401 before login, 401 for a wrong password, 200 for login, two
  scoped products with 14 provenance records, 200 for logout, and 401 afterward.

## Honest limits

This is real local session behavior with a MODELLED demo identity. The default local
credential is intentionally published for ease of demonstration and is never a
production secret. The module does not yet provide MFA, recovery, rate limiting, SSO,
device management, or security notifications. Local HTTP cannot set a useful `Secure`
cookie; the server adds that attribute when its public base URL is HTTPS.

## What comes next?

With buyer and merchant surfaces now understandable, the next slice can research and
implement UCP cart and checkout as an adapter over the existing cart/trusted-commit
model. It must not advertise checkout until current schemas, finalization, idempotency,
and recovery paths have executable tests.
